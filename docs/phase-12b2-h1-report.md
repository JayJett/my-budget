## Implementation

- `push-policy.js` is the server-side source for accepted routes. The migration embeds its expressions, with a check in Node and a PostgreSQL parity test. Both paths require a canonical HTTPS provider route on port 443 and keep the provider's case-sensitive subscription data. Non-provider or malformed legacy rows are retained and skipped before transport. Supported HTTP 404/410 cleanup still follows the existing behavior.
- `webpush.js` validates canonical unpadded base64url, a 65-byte uncompressed P-256 point and a 16-byte secret. Web Crypto checks the point; the database independently checks it against the curve. Encoding, key or attempt diagnostics remain outside public results. Fetch rejects redirects, gives each provider at most 8 seconds and does not automatically retry. `delivery.js` uses at most four sends in parallel and an 85-second delivery window, preserving inbox generation and existing reminder deduplication. Provider failures and suppressions return counts only.
- `20261123022923_push_destination_security.sql` keeps the existing RPC signatures and original rows. Only the owner can refresh a row. Same-input registration is idempotent and retains timestamps. Old and current FCM paths use one ownership key. Per-account and per-destination transaction locks serialize updates. New devices at the existing ten-device cap receive a message to remove one, with no automatic eviction. The non-unique canonical index accommodates historical aliases without rewriting rows.
- The private per-account limit is 20 accepted registration changes in a rolling hour and one accepted test per minute, at most five per rolling hour. Tests count independently of device removal, and same-input retries avoid consuming a registration slot. RLS and the RPC authentication boundary remain in force. These limits constrain accepted work per account. Rejected calls do not consume the registration budget.
- On a shared device, the app pins registration to the initiating sign-in. If the server returns an ownership conflict, the browser unsubscribes locally and asks for a second tap to register a fresh subscription. The previous account's server row is preserved. If local unsubscribe fails or the provider reissues the same endpoint, the user can turn it off from the original account or reset that browser's site registration.

## Production gates and staged release

1. **Obtain recovery evidence and owner approval.** Confirm the latest usable, encrypted production database export and separately recoverable Storage object copy. Record retention, access and a separately timed restore. Supabase Free alone does not establish these backups. Compare the live schema manifest with this targeted migration, confirm the vendor route inventory using counts only, and resolve any canonical URL collision between accounts before rollout. Historical conflicts need a separately approved resolution. Check Data API exposed schemas and the unresolved runner boundary. If evidence establishes browser reachability to an active runner capability, stop the normal release sequence and escalate for containment approval.
2. **Prove the matrix in an approved disposable environment.** Apply only the named H1 migration there. Use purpose-made accounts, synthetic subscriptions and isolated provider test devices. Exercise Chrome, Edge on Windows, Firefox, macOS Safari and the installed iPhone app. Validate normal test sends, opt-in changes, authorised removal/off, switched accounts, suppressed rows and low-volume scheduled delivery with no duplicate sends. Inspect counts and privacy only. Ensure the sandbox's reminder jobs cannot target production.
3. **Deploy the outbound guard first, after explicit approval.** Preserve the three dispatch modes and existing runner authentication. Verify delivery by provider with enrolment fixtures and check safe suppression, test results and inbox counts. Stage a guarded rollback artifact before this step. Avoid running two schedules or retrying a batch with ambiguous provider acceptance.
4. **Apply only the H1 migration after separate approval.** Take a fresh recovery point and match the reviewed target schema. Confirm no subscription rows were changed during the migration. Verify effective grants and rate limits with enrolled test accounts and observe only aggregate errors, conflicts and suppressed counts. Existing frontends still use the same registration RPC. Publish the client recovery guidance through the normal reviewed merge and Pages release only when the backend and compatibility gates pass.
5. **Stop criteria and rollback.** Stop if an off-policy destination reaches transport, a registration changes owner unexpectedly, providers reject previously verified subscriptions, or test/send counts duplicate or drift materially. Keep the hardened ownership and outbound validation when reverting client assets. Use a reviewed corrective migration or revert to the prepared guarded Edge version. A temporary pause of outbound push while retaining the authenticated inbox needs owner approval. Any restore is an incident action with known data-loss bounds and owner approval.

The draft involves no live Supabase writes, Edge deployments, Cron changes, key rotation or migration ledger changes. H2 is separate.
